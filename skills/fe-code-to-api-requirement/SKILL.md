# 前端程式碼 → 後端需求規格

把前端專案的程式碼，翻譯成一份**後端讀得懂、且不會被現有實作綁架**的需求規格，用來討論 API 該怎麼設計。

> **本 skill 不設計 API。** 不建議端點、不定義欄位、不決定 payload 形狀、不指定分頁或快取做法。那是後端的工作；本文件只提供他做決定所需的需求事實。

讀 [`CONTEXT.md`](CONTEXT.md)：選文件種類，並套用 **去實作化** 與 **畫面用詞**。若使用者要的是 TD Detail，讀 [td-detail-fillin](../td-detail-fillin/SKILL.md)。

## Trigger

使用者要求把某個畫面／功能／流程的前端程式碼，整理成給後端的需求描述或 API 需求規格時套用。

## 本文件獨有的硬規則（違反即重寫該段）

1. **不寫現況實作。** 不描述目前 API 如何處理，也不寫「目前前端會先呼叫 A 再呼叫 B」。「目前 API 沒有提供 X」本身就是現況描述，同樣不寫。現有 API 的端點、方法、參數、欄位名、回傳結構已由 CONTEXT.md **去實作化** 禁止。
2. **最低背景知識。** 假設讀者只知道「這是哪個產品的哪個畫面」，其餘一切在文件內交代完。正文出現的每個非通用中文名詞，都必須在「名詞說明」用一句話定義。
3. **不替後端決定做法。** 不指定端點數量、欄位名、payload 形狀、分頁或快取。

## Workflow

1. **圈定範圍** — 確認是哪個畫面／功能／使用者流程。範圍不明確就先問。
2. **讀真實程式碼抽事實** — 記在草稿，此階段可含實作細節。要抽的是：使用者能做什麼、畫面上會出現什麼資訊、什麼條件下結果會不同、什麼操作會改變資料。
3. **逐條去實作化** — 套用 CONTEXT.md。寫不出使用者看到什麼、得到什麼的，刪掉或回頭重抽。
4. **名詞收斂** — 掃過正文每一個名詞，套用下方「名詞規範」。優先沿用 畫面用詞。
5. **標出未決問題** — 程式碼看不出意圖、或現有行為疑似是將就實作而非真需求的，一律進「未決問題」，不要自行腦補成需求。
6. **跑交件前 Checklist**，再輸出。

**輸出去向**：預設輸出在對話中。使用者指定路徑時，寫成該 markdown 檔。

## 名詞規範

### 先定義才能用

正文出現的每個非通用中文名詞，都要在「名詞說明」給一句可驗證的定義，且**定義本身不能再引用另一個未定義的名詞**。畫面沒有對應詞時才改用全稱，並在名詞說明中定義。按鈕、欄位標題、篩選選項、狀態文字在第 0 節用一句話定義，詞本身沿用 畫面用詞。

### 易造成模糊解讀的用詞 → 改寫

| 避免 | 為什麼模糊 | 改寫方向 |
|---|---|---|
| 同步 | 沒說方向、時機、誰是來源 | 寫成「誰在什麼時候會看到什麼」 |
| 處理／支援／優化 | 沒有可驗證的結果 | 寫出使用者可觀察的結果 |
| 狀態 | 不知道是哪一組互斥值 | 「◯◯狀態，只會是 A、B、C 其中一種」並各給定義 |
| 聚合／彙整／組裝 | 聽起來像在指定做法 | 「同一個畫面上要同時看到…」 |
| 即時／自動 | 秒級？換頁後？重新整理後？ | 「使用者按下 X 之後，畫面上的 Y 要跟著改變」 |
| 快取／分頁／批次／非同步 | 都是實作手段 | 描述使用者需求，做法交給後端 |
| 一致／正確 | 沒有判準 | 寫出可比對的具體條件 |

### 有限取值的寫法

若某個資訊只有固定幾種可能，把每一種都列出來並各給一句定義；用中文語意描述，**不要抄程式碼裡的常數字面值**，也不要暗示後端該用什麼值表示。

## 輸出格式

```markdown
# [畫面／功能名稱] 需求規格（給後端）

## 0. 名詞說明
| 名詞 | 一句話定義 |
|---|---|
| | |

## 1. 這個功能在做什麼
（三到五句，從使用者角度描述目的與價值）

## 2. 使用者可以做的事
- [動作]：誰、在什麼情況下可以做、做完之後看到什麼結果

## 3. 畫面上需要呈現的資訊
| 資訊項目 | 一句話定義 | 什麼時機需要出現 | 是否必須與其他項目同時呈現 |
|---|---|---|---|
| | | | |

## 4. 會改變資料的操作
- [操作]：什麼條件下可以觸發、改變了什麼、使用者如何得知成功或失敗

## 5. 判斷規則
- 當 [條件] 時，[可觀察的結果]
（條件與結果一律使用第 0 節定義過的名詞）

## 6. 未決問題／待後端確認
- [ ] 問題敘述（以「這個需求是否成立」的形式提問，不預設做法）
```

第 3 節的「是否必須與其他項目同時呈現」是要讓後端判斷資料該怎麼組合，**但不要替他決定要幾支 API 或怎麼組**。

不適用的章節可省略，但第 0、1、6 節必留。

## Example

**不合格**（去實作化 + 現況敘述）：

```
FilterService 的 applyLicenseFilter() 會把裝置清單 API 回傳的 devices[].licenses[].status
為 ACTIVE 的項目留下。因為現行 API 沒有提供未授權旗標，前端額外推算後補上。
```

**合格**：

```
使用者在裝置清單上選擇「授權有效」時，清單只留下至少有一筆授權仍在有效期間內的裝置。

名詞說明
- 授權有效：該裝置目前擁有的授權中，至少一筆的有效期間涵蓋今天。

未決問題
- [ ] 一台裝置若同時有有效與已過期的授權，是否應該被「授權有效」選中？
```

**不合格**（自創專有名詞，違反 畫面用詞）：

```
使用者可依「許可憑證生命週期」篩選裝置。
```

畫面上寫的是「授權有效」，正文就要用「授權有效」。

## 交件前 Checklist

```
- [ ] 已讀 CONTEXT.md；正文通過 去實作化 與 畫面用詞
- [ ] 正文無「目前後端如何處理」「目前 API 沒有提供」這類現況敘述
- [ ] 正文未替後端決定端點數量、欄位名、payload 形狀、分頁或快取做法
- [ ] 每個非通用名詞都在第 0 節定義過，且定義未引用未定義的名詞
- [ ] 無「同步／處理／優化／即時／聚合」等模糊用詞，或已改寫成可觀察結果
- [ ] 有限取值的資訊已列出所有可能，並各有一句定義
- [ ] 每條判斷規則都寫成「條件 → 使用者可觀察的結果」
- [ ] 程式碼看不出意圖、或疑似將就實作的部分，已進第 6 節而非被寫成需求
- [ ] 通篇繁體中文產品語言
```
