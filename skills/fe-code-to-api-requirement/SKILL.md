# 前端程式碼 → 後端需求規格

把前端專案的程式碼，翻譯成一份**後端讀得懂、且不會被現有實作綁架**的需求規格，用來討論 API 該怎麼設計。

> **本 skill 不設計 API。** 不建議端點、不定義欄位、不決定 payload 形狀、不指定分頁或快取做法。那是後端的工作；本文件只提供他做決定所需的需求事實。

## Trigger

使用者要求把某個畫面／功能／流程的前端程式碼，整理成給後端的需求描述或 API 需求規格時套用。

## 與 td-detail-fillin 的差異（先選對 skill）

| | 本 skill | `td-detail-fillin` |
|---|---|---|
| 目的 | 重新討論 API 該怎麼設計 | 對齊既有 API、收斂技術債 |
| 現行 API 欄位路徑 | **禁止出現** | 必寫且要寫完整 |
| 現況前端推算 | **禁止出現** | 必須與直通 API 分開寫清 |

若使用者要的是「對照現行 API 寫 TD Detail」，改用 `td-detail-fillin`。

---

## 四條硬規則（違反即重寫該段）

1. **不寫現況實作。** 不描述目前 API 如何處理，不出現任何現有 API 的端點、方法、參數、欄位名、回傳結構，也不寫「目前前端會先呼叫 A 再呼叫 B」這類流程敘述。「目前 API 沒有提供 X」本身就是現況描述，同樣不寫。
2. **不寫前端實作名稱。** 正文不出現變數名、函數名、類別名、元件名、檔案路徑、狀態管理容器名稱、程式碼裡的常數字面值。
3. **最低背景知識。** 假設讀者只知道「這是哪個產品的哪個畫面」，其餘一切在文件內交代完。正文出現的每個非通用中文名詞，都必須在「名詞說明」用一句話定義。
4. **用畫面上看得到的詞。** 可以允許使用一般使用者在UI介面上可以看到的詞彙，不要自己發明專有名詞來影響文件閱讀而造成誤解。

程式碼證據（檔案、行號、欄位、函數名）可以留在你的分析草稿裡，用來確保正確性；**但不得出現在交付正文**。

---

## Workflow

1. **圈定範圍** — 確認是哪個畫面／功能／使用者流程。範圍不明確就先問。
2. **讀真實程式碼抽事實** — 記在草稿，此階段可含實作細節。要抽的是：使用者能做什麼、畫面上會出現什麼資訊、什麼條件下結果會不同、什麼操作會改變資料。
3. **逐條去實作化** — 每條問自己：「拿掉這些名字之後，使用者看到什麼、得到什麼？」寫不出來的，代表你抽到的是實作細節而不是需求，刪掉或回頭重抽。畫面上使用者看得到的詞要留下來，不要另外發明專有名詞取代。
4. **名詞收斂** — 掃過正文每一個名詞，套用下方「名詞規範」。優先沿用 UI 文案。
5. **標出未決問題** — 程式碼看不出意圖、或現有行為疑似是將就實作而非真需求的，一律進「未決問題」，不要自行腦補成需求。
6. **跑交件前 Checklist**，再輸出。

**輸出去向**：預設輸出在對話中。使用者指定路徑時，寫成該 markdown 檔。

## 去實作化改寫對照

| 草稿寫法（禁止進正文） | 正文改寫 |
|---|---|
| 判斷授權欄位等於 `ACTIVE` | 該授權仍在有效期間內 |
| 取得清單後在前端過濾 | 使用者選定條件後，清單只留下符合條件的項目 |
| 回傳結構中一個裝置底下有多筆授權陣列 | 一台裝置可能同時擁有多筆授權 |
| 前端用對照表反查機型名稱 | 使用者需要看到機型的完整名稱，而不是型號代碼 |
| 目前 API 沒給到期日，所以前端自己算 | 使用者需要在清單上直接看到距離到期還有幾天 |
| 送出前先呼叫試算 API 檢查 | 使用者按下送出前，需要先知道這次操作會造成什麼結果 |
| 把畫面「授權有效」改寫成「許可憑證生命週期」 | 沿用畫面上的「授權有效」 |

倒數第二列起是最容易犯規的地方：**只寫「使用者需要什麼」，不寫「現在是怎麼做到的」**；畫面文案直接沿用，不要另造專有名詞。

## 名詞規範

### 先用畫面上的詞，再定義

可以允許使用一般使用者在UI介面上可以看到的詞彙，不要自己發明專有名詞來影響文件閱讀而造成誤解。

按鈕、欄位標題、篩選選項、狀態文字、提示——畫面上已經寫給使用者看的詞，正文直接沿用，並在第 0 節用一句話定義。去實作化改掉的是程式碼名稱，不是畫面文案。

### 先定義才能用

正文出現的每個非通用中文名詞，都要在「名詞說明」給一句可驗證的定義，且**定義本身不能再引用另一個未定義的名詞**。程式碼／內部文件用的縮寫與代號，改成畫面上使用者看得到的詞；畫面沒有對應詞時才改用全稱，並在名詞說明中定義。

### 易造成模糊解讀的用詞 → 改寫

| 避免 | 為什麼模糊 | 改寫方向 |
|---|---|---|
| 同步 | 沒說方向、時機、誰是來源 | 寫成「誰在什麼時候會看到什麼」 |
| 處理／支援／優化 | 沒有可驗證的結果 | 寫出使用者可觀察的結果 |
| 狀態 | 不知道是哪一組互斥值 | 「◯◯狀態，只會是 A、B、C 其中一種」並各給定義 |
| 聚合／彙整／組裝 | 聽起來像在指定做法 | 「同一個畫面上要同時看到…」 |
| 即時／自動 | 秒級？換頁後？重新整理後？ | 「使用者按下 X 之後，畫面上的 Y 要跟著改變」 |
| 快取／分頁／批次／非同步 | 都是實作手段 | 描述使用者需求，做法交給後端 |
| 一致／正確 | 沒有判準 | 寫出可比對的具體條件 |

### 有限取值的寫法

若某個資訊只有固定幾種可能，把每一種都列出來並各給一句定義；用中文語意描述，**不要抄程式碼裡的常數字面值**，也不要暗示後端該用什麼值表示。

## 輸出格式

```markdown
# [畫面／功能名稱] 需求規格（給後端）

## 0. 名詞說明
| 名詞 | 一句話定義 |
|---|---|
| | |

## 1. 這個功能在做什麼
（三到五句，從使用者角度描述目的與價值）

## 2. 使用者可以做的事
- [動作]：誰、在什麼情況下可以做、做完之後看到什麼結果

## 3. 畫面上需要呈現的資訊
| 資訊項目 | 一句話定義 | 什麼時機需要出現 | 是否必須與其他項目同時呈現 |
|---|---|---|---|
| | | | |

## 4. 會改變資料的操作
- [操作]：什麼條件下可以觸發、改變了什麼、使用者如何得知成功或失敗

## 5. 判斷規則
- 當 [條件] 時，[可觀察的結果]
（條件與結果一律使用第 0 節定義過的名詞）

## 6. 未決問題／待後端確認
- [ ] 問題敘述（以「這個需求是否成立」的形式提問，不預設做法）
```

第 3 節的「是否必須與其他項目同時呈現」是要讓後端判斷資料該怎麼組合，**但不要替他決定要幾支 API 或怎麼組**。

不適用的章節可省略，但第 0、1、6 節必留。

---

## Example

**不合格**（同時違反硬規則 1–3）：

```
FilterService 的 applyLicenseFilter() 會把裝置清單 API 回傳的 devices[].licenses[].status
為 ACTIVE 的項目留下。因為現行 API 沒有提供未授權旗標，前端額外推算後補上。
```

**合格**：

```
使用者在裝置清單上選擇「授權有效」時，清單只留下至少有一筆授權仍在有效期間內的裝置。

名詞說明
- 授權有效：該裝置目前擁有的授權中，至少一筆的有效期間涵蓋今天。

未決問題
- [ ] 一台裝置若同時有有效與已過期的授權，是否應該被「授權有效」選中？
```

**不合格**（違反硬規則 4，自創專有名詞）：

```
使用者可依「許可憑證生命週期」篩選裝置。
```

畫面上寫的是「授權有效」，正文就要用「授權有效」，不要另造一個看起來更專業的詞。

## 交件前 Checklist

交付前逐項確認：

```
- [ ] 正文無任何現有 API 的端點、方法、參數、欄位名或回傳結構
- [ ] 正文無「目前後端如何處理」「目前 API 沒有提供」這類現況敘述
- [ ] 正文無前端變數名、函數名、類別名、元件名、檔案路徑、程式碼常數字面值
- [ ] 正文未替後端決定端點數量、欄位名、payload 形狀、分頁或快取做法
- [ ] 每個非通用名詞都在第 0 節定義過，且定義未引用未定義的名詞
- [ ] 正文用的是畫面上使用者看得到的詞，沒有自創專有名詞
- [ ] 無「同步／處理／優化／即時／聚合」等模糊用詞，或已改寫成可觀察結果
- [ ] 有限取值的資訊已列出所有可能，並各有一句定義
- [ ] 每條判斷規則都寫成「條件 → 使用者可觀察的結果」
- [ ] 程式碼看不出意圖、或疑似將就實作的部分，已進第 6 節而非被寫成需求
- [ ] 通篇繁體中文產品語言，未參雜前端術語
```
